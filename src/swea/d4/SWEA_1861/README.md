# SWEA 1861. 정사각형 방

## 1. 문제를 통해 배운 핵심

이 문제는 처음에는 **2차원 배열에서 상하좌우로 이동하는 탐색 문제**로 접근했다.

하지만 풀이를 발전시키면서 다음과 같은 내용을 학습할 수 있었다.

1. 4방향 탐색이라고 해서 반드시 BFS/DFS를 사용할 필요는 없다.
2. `visited`는 단순한 방문 체크 이외의 의미로도 사용할 수 있다.
3. 이미 계산한 결과를 저장하면 중복 탐색을 줄일 수 있다.
4. `visited`에서 한 단계 발전하면 **DP / 메모이제이션**으로 연결할 수 있다.
5. 문제의 조건을 적극적으로 활용하면 탐색 자체를 없앨 수도 있다.
6. 좌표 간 상하좌우 인접 여부를 **맨해튼 거리**로 판단할 수 있다.

---

# 2. 첫 번째 접근 - 직접 경로 따라가기

처음에는 모든 방을 시작점으로 확인하면서 현재 방보다 정확히 `1` 큰 방을 상하좌우에서 찾았다.

```java
int[] dx = {0, 0, -1, 1};
int[] dy = {1, -1, 0, 0};
```

현재 위치가 `(x, y)`라면 다음 방을 다음과 같이 탐색할 수 있다.

```java
for (int k = 0; k < 4; k++) {
    int nx = x + dx[k];
    int ny = y + dy[k];

    if (nx < 0 || nx >= N || ny < 0 || ny >= N) {
        continue;
    }

    if (rooms[nx][ny] == rooms[x][y] + 1) {
        x = nx;
        y = ny;
        cnt++;
        break;
    }
}
```

### BFS/DFS가 필요하지 않았던 이유

처음에는 4방향 탐색이므로 BFS/DFS 문제처럼 보였다.

하지만 이 문제에서는 모든 방의 번호가 서로 다르고 다음 방의 조건이

```text
현재 방 번호 + 1
```

이기 때문에 다음 방은 **최대 하나만 존재한다.**

즉 일반적인 그래프 탐색처럼

```text
        A
      / | \
     B  C  D
```

여러 경로로 분기되는 것이 아니라

```text
5 → 6 → 7 → 8
```

하나의 경로만 만들어진다.

따라서 Queue를 사용하는 BFS나 재귀/Stack을 사용하는 DFS가 반드시 필요한 문제가 아니다.

> **4방향 탐색 = BFS/DFS는 아니다.**
>
> 탐색 가능한 경로가 어떻게 구성되는지를 먼저 확인해야 한다.

---

# 3. `visited`를 이용한 첫 번째 최적화

처음에는

```java
boolean[][] visited = new boolean[N][N];
```

를 사용했다.

하지만 일반적인 BFS/DFS의 `visited`와 사용 목적이 조금 달랐다.

경로가

```text
5 → 6 → 7 → 8
```

이라면 각각의 시작점에서 가능한 길이는

```text
5 : 4
6 : 3
7 : 2
8 : 1
```

이다.

따라서 `5`에서 출발하여 `6, 7, 8`까지 이미 탐색했다면 `6`, `7`, `8`을 새로운 시작점으로 다시 검사할 필요가 없다.

그래서 바깥 반복문에서는

```java
if (visited[i][j]) {
    continue;
}
```

로 해당 방을 새로운 시작점에서 제외했다.

### 중요한 점

실제 경로를 탐색할 때는 `visited`를 검사하면 안 된다.

예를 들어 배열의 탐색 순서 때문에 먼저

```text
6 → 7 → 8
```

을 발견했다고 하자.

이후 `5`에서 탐색하면

```text
5 → 6 → 7 → 8
```

까지 이동해야 정확한 길이 4를 구할 수 있다.

따라서 이 풀이에서 `visited`의 의미는

> **이 방에 방문한 적이 있는가?**

보다는

> **이 방을 새로운 시작점으로 다시 탐색할 필요가 있는가?**

에 가까웠다.

---

# 4. visited → DP / 메모이제이션

`visited`를 사용하면서 한 가지 개선점을 발견할 수 있었다.

기존에는

```text
6을 이미 지나갔다는 사실
```

만 저장한다.

그런데 이왕 탐색했다면

```text
6에서 출발하면 몇 개의 방을 갈 수 있는지
```

까지 저장할 수 있다.

이를 위해

```java
int[][] dp = new int[N][N];
```

를 사용했다.

DP의 의미는 다음과 같이 정의했다.

```text
dp[x][y]
= (x, y)에서 출발했을 때 이동할 수 있는 총 방의 개수
```

예를 들어

```text
5 → 6 → 7 → 8
```

이라면

```text
dp[5] = 4
dp[6] = 3
dp[7] = 2
dp[8] = 1
```

이 된다.

---

## 5. 메모이제이션의 장점

이미

```text
6 → 7 → 8
```

을 탐색해서

```text
dp[6] = 3
```

이라는 사실을 알고 있다고 하자.

이후 `5`에서 출발했을 때 기존 방식은 다시

```text
5 → 6 → 7 → 8
```

을 전부 탐색한다.

하지만 DP를 사용하면 `6`을 만나는 순간

```java
cnt += dp[x][y];
```

를 통해

```text
dp[5] = 1 + dp[6]
      = 1 + 3
      = 4
```

로 계산할 수 있다.

즉,

```text
visited
"여기에 와본 적이 있는가?"

        ↓ 발전

memoization
"여기에서 출발했을 때의 정답을 이미 알고 있는가?"
```

로 사고를 확장할 수 있었다.

> **단순히 계산했다는 사실만 저장하지 말고, 계산한 결과 자체를 저장하면 중복 연산을 줄일 수 있다.**

---

# 6. 경로 전체의 DP 값 저장

경로를 한 번 탐색했다면 시작점뿐만 아니라 중간 방의 결과도 저장하는 것이 좋다.

예를 들어

```text
5 → 6 → 7 → 8
```

을 탐색했다면 결과를

```text
5 = 4
6 = 3
7 = 2
8 = 1
```

로 저장한다.

이를 위해 탐색 과정의 좌표를 저장했다.

```java
List<int[]> path = new ArrayList<>();
```

탐색이 끝난 뒤 경로를 이용하여 각각의 DP 값을 계산할 수 있다.

이 과정을 통해 **한 번 계산한 문제의 결과를 이후 계산에서 재사용하는 메모이제이션**의 기본 원리를 이해할 수 있었다.

---

# 7. 최종 개선 - 방 번호를 이용한 좌표 저장

DP 풀이 이후 문제의 조건을 다시 확인하면 더 단순한 풀이가 가능하다.

이 문제에서는

```text
1 ~ N²
```

의 방 번호가 **각각 정확히 한 번씩 등장한다.**

따라서 `rooms[x][y]`를 이용해 매번 `+1`인 방을 찾는 대신,

> **방 번호 → 좌표**

관계를 미리 저장할 수 있다.

```java
int[][] position = new int[N * N + 1][2];
```

입력을 받을 때

```java
int num = Integer.parseInt(st.nextToken());

position[num][0] = i;
position[num][1] = j;
```

로 저장하면

```text
position[1] = 1번 방 좌표
position[2] = 2번 방 좌표
position[3] = 3번 방 좌표
...
```

를 O(1)에 확인할 수 있다.

이제 `5`에서 `6`으로 이동 가능한지를 확인하기 위해 5번 방의 상하좌우를 탐색할 필요가 없다.

그냥

```text
5번 방의 좌표
6번 방의 좌표
```

가 서로 붙어 있는지만 확인하면 된다.

---

# 8. 맨해튼 거리

두 좌표가

```text
(x1, y1)
(x2, y2)
```

일 때 상하좌우로 바로 붙어 있다면

```text
|x1 - x2| + |y1 - y2| = 1
```

이 성립한다.

Java에서는

```java
Math.abs(x1 - x2) + Math.abs(y1 - y2) == 1
```

로 확인할 수 있다.

따라서 `i`번 방과 `i-1`번 방이 연결되어 있는지는

```java
if (Math.abs(A[i][0] - A[i - 1][0])
        + Math.abs(A[i][1] - A[i - 1][1]) == 1) {
    cur++;
} else {
    cur = 1;
}
```

만으로 확인할 수 있다.

이를 통해 기존의 **4방향 탐색 자체를 제거**할 수 있었다.

---

# 9. 큰 번호부터 탐색한 이유

최종 풀이에서는 큰 번호부터 작은 번호 방향으로 확인했다.

```java
for (int i = N * N; i > 0; i--) {
    ...
}
```

예를 들어

```text
5 → 6 → 7 → 8
```

이라면 역방향으로 확인하면서

```text
8
7 → 8
6 → 7 → 8
5 → 6 → 7 → 8
```

처럼 연속된 길이를 `cur` 하나로 관리할 수 있다.

또한 문제에서는 최대 이동 횟수가 동일하면 **시작 방 번호가 작은 것을 선택**해야 한다.

큰 번호부터 작은 번호로 탐색하고 있으므로

```java
if (cur >= maxCnt) {
    maxCnt = cur;
    maxIdx = i;
}
```

처럼 `>=`를 사용하면 동일한 길이가 나왔을 때 나중에 등장한 더 작은 방 번호로 자연스럽게 갱신된다.

# 10. 시간복잡도

## 초기 4방향 탐색

각 방을 시작점으로 탐색하고 연결된 방을 직접 따라가는 방식이다.

중복 경로 탐색이 발생할 수 있다.

---

## 메모이제이션 적용

이미 계산한 경로의 결과를 `dp`에 저장하여 중복 탐색을 줄인다.

```text
dp[x][y] = 해당 방에서 시작했을 때의 이동 길이
```

---

## 좌표 저장 방식

입력 시 모든 방의 위치를 저장한다.

```text
입력: O(N²)
방 번호 비교: O(N²)
```

따라서 전체 시간복잡도는

```text
O(N²)
```

이다.

추가 공간 역시 방의 위치를 저장하기 위해

```text
O(N²)
```

을 사용한다.

# 11. 코드 작성 과정에서 얻은 Java 포인트

### `Integer[]`보다 `int[]`

경로를 저장할 때

```java
List<Integer[]> path
```

보다는

```java
List<int[]> path
```

를 사용하는 것이 좋다.

`Integer`는 객체이므로 불필요한 객체 생성과 Boxing/Unboxing이 발생할 수 있다.

코딩테스트에서는 특별한 이유가 없다면 primitive type을 우선 고려한다.

---

### 입력 반복문의 인덱스 확인

최종 풀이를 작성하면서

```java
for (int j = 1; j < N; j++)
```

로 작성하여 한 행에서 `N-1`개의 숫자만 읽는 실수가 있었다.

2차원 배열 입력의 일반적인 형태는

```java
for (int i = 0; i < N; i++) {
    StringTokenizer st = new StringTokenizer(br.readLine());

    for (int j = 0; j < N; j++) {
        ...
    }
}
```

이다.

알고리즘 로직이 맞더라도 **입력 범위와 반복문의 시작/종료 조건** 때문에 오답이 발생할 수 있으므로 제출 전 확인해야 한다.

# 12. 이 문제에서 가장 중요했던 사고 과정

이 문제의 풀이 과정은 다음과 같이 발전했다.

```text
[1] 2차원 배열에서 직접 4방향 탐색

             ↓

[2] 이미 경로에 포함된 방은
    시작점으로 다시 볼 필요가 없다는 것을 발견

             ↓

[3] boolean visited 사용

             ↓

[4] "방문했다는 사실만 저장할 필요가 있나?"
    "그 방에서 갈 수 있는 길이까지 저장하면?"

             ↓

[5] int[][] dp를 이용한 메모이제이션

             ↓

[6] 문제 조건 재확인
    1 ~ N²가 정확히 한 번씩 등장

             ↓

[7] 방 번호별 좌표를 미리 저장

             ↓

[8] 4방향 탐색 제거
    맨해튼 거리로 i와 i+1의 인접 여부 확인

             ↓

[9] O(N²)의 단순한 풀이
```

# 13. 최종 학습 포인트 ⭐

### 1. 4방향 이동 문제라고 무조건 BFS/DFS는 아니다.

분기가 존재하는지, 다음 이동 후보가 몇 개인지를 먼저 확인한다.

### 2. `visited`의 의미를 직접 정의하자.

`visited`가 항상 단순히

```text
방문했다 / 방문하지 않았다
```

를 의미할 필요는 없다.

현재 알고리즘에서 왜 필요한지 생각해야 한다.

### 3. 방문 여부보다 계산 결과를 저장하는 것이 더 유용할 수 있다.

```text
boolean visited
        ↓
int dp
```

로 발전시키면서 메모이제이션의 필요성을 이해할 수 있었다.

### 4. DP는 단순히 점화식을 외우는 것이 아니다.

```text
"이거 전에 계산했는데 또 계산하고 있네?"
```

라는 중복 연산을 발견하고,

```text
"그럼 이전 계산 결과를 저장해서 다시 사용하면 되지 않을까?"
```

라고 생각하는 것 역시 DP의 핵심적인 접근이다.

### 5. 문제의 특별한 조건을 적극적으로 이용하자.

이 문제에서 가장 강력한 조건은

```text
1 ~ N²의 숫자가 정확히 한 번씩 등장한다.
```

는 것이다.

이 조건 덕분에

```text
좌표 → 방 번호
```

뿐만 아니라

```text
방 번호 → 좌표
```

로 문제를 뒤집어 생각할 수 있었다.

### 6. 탐색을 빠르게 하는 것보다 탐색을 없앨 수 있는지 먼저 생각하자.

처음에는 4방향 탐색을 어떻게 최적화할지를 고민했지만 최종적으로는 방 번호별 좌표를 저장함으로써 **4방향 탐색 자체가 필요 없어졌다.**

---

## 한 줄 정리

> **SWEA 1861을 통해 단순 4방향 탐색에서 시작하여 `visited → 메모이제이션 → 문제 조건을 활용한 O(N²) 좌표 기반 풀이`로 최적화하는 과정을 학습했다.**
